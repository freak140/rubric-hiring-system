What I built:

Problems I hit and how I fixed them:
- The autogenerated migration created foreign keys and the unique constraint with no explicit names (`op.create_foreign_key(None, ...)`), which made `downgrade()` uncallable (`drop_constraint(None, ...)`). Gave them explicit names matching Postgres's own default naming convention in both directions.
- First test run failed: in-memory `Application()` objects had `stage=None` instead of the model's declared default. SQLAlchemy's `mapped_column(default=...)` only applies at INSERT/flush time, not on plain Python construction — fixed by having the test factory set `stage=ApplicationStage.sourced` explicitly.
- Two gate tests failed the same way: `gate_focused_to_references` compared `rating.scorecard_item_id` (the raw FK scalar), which likewise is only populated by a flush, not by assigning the `scorecard_item` relationship in memory. Fixed by comparing `rating.scorecard_item.id` instead, which is populated immediately since it's a direct object reference. Also fixed the same latent bug in `workflow.create_default_safeguarding_checks`, which was setting `application_id=application.id` instead of `application=application` — the former wouldn't show up in `application.safeguarding_checks` until a DB round-trip, which would have silently broken the very next gate check in the same request.

Decisions I made:
- `advance_application`'s `override_reason` behavior: a non-chairman actor supplying any override reason raises `WorkflowError` ("refused" as an authorization error); a chairman supplying a blank/missing override reason against a blocked gate just falls through to the normal blocked `GateResult` (no exception) — the prompt's "refused" for that case reads as "the move does not happen," not "a wrong-role security violation," so only the wrong-role path raises.
- Invalid stage transitions (skipping a stage, moving backward, or acting on an application already in a terminal stage) raise `WorkflowError`, not a `GateResult` — these are programming/UI errors (the UI should only ever offer the valid next move), not a business-rule judgment call with reasons to show a user.
- `reject`/`withdraw` go through `advance_application` as well, as a separate branch (reason required, no gate function, allowed from any non-terminal stage) rather than a separate service function — keeps the single "the one way state changes happen" entry point from the prompt's "every state change goes through app/services."
- `can_view_ratings` treats "submitted their own rating" as: the user has at least one rating recorded on any interview of theirs for that application (not necessarily the specific `interview` argument) — matches "after submitting their own" without requiring them to have rated every scorecard item first.

## Phase 5: AI assistance

What I built:
- `app/services/ai/client.py`: `call_llm(system_prompt, user_prompt, schema)` tries Groq then Gemini (skipping any provider with no API key configured), each with one retry-after-backoff on `RateLimitError`/5xx, and one retry with the validation error appended if the JSON response fails the Pydantic schema; falling all the way through raises `AIUnavailableError("AI is unavailable right now. Please continue manually.")`. `call_llm_cached(db, task, input_data, prompt_version, ...)` looks up `AIOutput` by `(task, sha256(input_data + prompt_version))` before calling, and stores every fresh result with provider/model/prompt_version. `peek_cache(...)` is a read-only lookup (never calls the LLM) used by GET routes to display a previously-generated draft without triggering a new API call on every page view.
- `app/services/ai/prompts.py`: one versioned system+user prompt pair per feature, every system prompt stating the model never grades/scores/ranks/recommends.
- `app/services/ai/schemas.py`: a Pydantic schema per feature, each with no grade/score/rank field by construction (not just by prompt instruction) — `ScorecardDraft.outcomes`/`competencies` enforce the 3-8/4-8 counts from the spec via `Field(min_length=..., max_length=...)`.
- `app/services/ai/features.py`: `draft_scorecard`, `generate_focused_questions` (+ its `peek_` counterpart), `map_evidence` (filters the model's quotes through `_verified_quotes`, which discards anything that isn't an exact substring of the notes, before returning), `summarize_decision` (+ its `peek_` counterpart).
- UI wiring, each gated on `settings.AI_ENABLED` both in the template (hide the button) and in the route (refuse the POST even if someone bypasses the UI), each logged via `log_event` with provider/model/cached, each labelled "AI draft: review before use":
  - Opening detail: "Draft scorecard with AI" (brief -> mission + outcomes + competencies inserted as draft items, not auto-approved).
  - Focused/demo-lesson interview form: "Generate interview questions (AI)" above the rating fields, and an HTMX-powered "Suggest evidence (AI)" button next to the notes textarea that posts the live (unsaved) textarea content to `/interviews/{id}/ai/evidence-map` and swaps in a server-rendered partial (`interviews/_evidence_panel.html`) — chosen over a full-page round trip specifically so the interviewer doesn't lose their in-progress grades/evidence while drafting notes.
  - Decision section of the application page: "Summarise evidence (AI)" producing a neutral paragraph over ratings+evidence+completed-reference-notes, with no recommendation.
- `scripts/eval_evidence.py`: 3 hand-labelled samples (maths teacher, librarian, accounts officer), matched by *position* in the returned list (see below), printing per-item and overall precision/recall.
- 8 pytest tests with the API fully mocked: the quote-verification guard, cache-hit skips the LLM entirely, cache-miss stores the result, provider fallback on a hard failure, the validation-retry-then-succeed path, validation failing twice moving to the next provider, and both "no providers configured" / "every provider fails" raising `AIUnavailableError`.

Problems I hit and how I fixed them:
- **Both configured default models were dead.** `.env` (and `.env.example`/`app/config.py` defaults) had `GROQ_MODEL=llama-3.3-70b-versatile` and `GEMINI_MODEL=gemini-2.0-flash`, both retired by their providers (confirmed via `NotFoundError` from each API directly, then by listing each provider's live `/models`). This is exactly the scenario the fallback chain exists for, and it worked correctly — both providers failed and the UI showed "AI is unavailable right now," not a 500. Still, a demo with AI permanently unavailable isn't a good demo, so I updated the three places that name a default model (`.env`, `.env.example`, `app/config.py`) to currently-live models (`openai/gpt-oss-20b` on Groq, `gemini-2.5-flash` on Gemini), verified live.
- **The eval script's first run showed 0% recall on the first sample**, even though the feature's own quote-verification guard was working correctly. Root cause: the model sometimes echoes `scorecard_item_title` as `"Title: full description"` instead of the bare title, so looking the result up by exact title string (as the eval script did) silently missed it. The actual UI (`_evidence_panel.html`) never does this lookup — it just prints whatever title string comes back next to its quotes — so production behavior was unaffected; only the eval script's scoring was wrong. Fixed the eval script to match by *position* in the returned list instead of by title text (the prompt guarantees one entry per scorecard item in the same input order), and tightened the prompt wording to ask for the bare title verbatim, bumping `EVIDENCE_MAPPING_PROMPT_VERSION` to `v2` so old cached rows under the looser wording aren't served as if they were generated under the new one.
- Hit the same Windows console (cp1252) `UnicodeEncodeError` a few times printing AI-generated text with smart quotes/em-dashes directly to the terminal during manual debugging — not a bug in the app (Postgres stores it as UTF-8 fine, and Jinja/HTML rendering is unaffected); just don't `print()` raw AI output to this particular terminal.

Decisions I made:
- `peek_cache`/`peek_focused_questions`/`peek_decision_summary` exist so a GET request can show a previously-generated draft without ever calling the LLM on page load; only the explicit "Generate"/"Regenerate" button triggers a real (possibly cached) call. This wasn't spelled out in the prompt but follows directly from "AIOutput caching" plus buttons implying an explicit user action, and keeps page loads free of surprise API calls or spend.
- Evidence mapping's cache key includes the interview notes text itself, so if the interviewer edits their notes after a first "Suggest evidence" click, the next click is a fresh (uncached) call against the new text — correct behavior, not a bug, since the input genuinely changed.
- `map_evidence`'s quote filtering happens every time the result is used (cached or fresh), not only at write time, as cheap defense in depth; it has no real effect beyond the first filtering since the cached row's quotes are already clean, but it means any future change to the guard logic self-heals previously-cached rows without needing a cache bust.
- Live-tested all four features end-to-end against real Groq/Gemini traffic (not just the mocked unit tests) specifically because CLAUDE.md's "AI never grades/scores/ranks/recommends" and "works with AI_ENABLED=false" are product guarantees, not just code shape — worth confirming the real model's output actually honors the prompt (it did: the decision summary restated grades as facts, never as a verdict) and that every AI control point (button visibility and the route itself) is actually inert with the flag off, not just visually hidden.

Problems I hit and how I fixed them:
- **First seed run crashed**: `'decision' is not the next stage after 'focused'`. Root cause was a real, useful one: `gate_focused_to_references` (built and tested back in Phase 1) correctly requires *every* completed focused/demo-lesson interview to rate *every* scorecard item -- and Priya's demo lesson had only rated 2 of the 4 items, since narratively a demo lesson doesn't obviously touch "lesson plans on time" or "parent communication." `advance_application` doesn't raise when a gate blocks a *valid* forward move (that's correct, normal behavior for a real blocked gate) -- it just returns `allowed=False` and leaves the stage unchanged, so the failure only surfaced two calls later as a confusing unrelated error. Fixed the data (both the focused interview and the demo lesson now rate all 4 items, with a plausible in-lesson observation invented for the two lesson-plan/parent-communication items), and added a strict `advance()` wrapper in the seed script that raises immediately with the gate's actual reasons if a seed step doesn't satisfy its gate, so any future seed-data mistake fails loudly at the right line instead of several calls downstream.
- **`POST /demo/reset` hung indefinitely** the first time it was exercised through the running app (not just as a standalone script). Root cause: `reset_confirmed` depends on `get_template_context`, which opens a request-scoped DB session and does a `SELECT` on `users` (for the current user and the role-switcher list) that stays open as part of the request's transaction; `run_seed()` then opens a *second* session and tries to `TRUNCATE` the same tables, which needs an exclusive lock that Postgres won't grant while the first session's read transaction is still open -- a self-deadlock. Fixed by adding `db: Session = Depends(get_db)` as an explicit second parameter on the route (FastAPI's dependency cache means this resolves to the *same* session instance `get_template_context` is already using) and calling `db.close()` on it before invoking `run_seed()`. Caught this by timing out waiting for the POST in a live walkthrough, not by any unit test -- a reminder that a feature touching its own request's session plus a side session needs this checked by hand.
- Refactored `_ratings_text`/`_references_text` out of `app/routers/applications.py` into `app/services/ai/features.py` as public `ratings_text_for`/`references_text_for` (alongside the existing `_*_input` builders) specifically so `scripts/seed.py` could reuse the exact same logic for the pre-generated `decision_summary` row without importing a FastAPI router module (which would register routes as a side effect) into a plain script. Also renamed `client._input_hash` to the public `compute_input_hash` for the same reason -- the seed script needed to call it directly.

Decisions I made:
- Chose to drive almost all seed data through the real `advance_application`/`approve_scorecard` service functions rather than setting `application.stage` directly, even though it's more code and found the two bugs above. This was a deliberate trade: slower to write, but the seed data is now provably gate-consistent (if a future code change breaks a gate, the seed script breaks too, loudly), and the audit trail it produces is byte-for-byte what the real app would have produced for that sequence of actions -- valuable for a dashboard/audit-log demo.
- Only one of the four pre-generated `AIOutput` rows (focused questions for the Maths opening) is actually reachable via a live button click in the seeded end-state, since the other three correspond to interviews/decisions that are already `completed`/decided (and those AI buttons correctly hide once an interview is completed or an application has moved past `decision`). This is fine and expected: two of the four Maths candidates are deliberately left *complete* (hired) or *blocked* rather than mid-interview, and the AI scorecard-drafting step of the tour is explicitly about a *new* opening the visitor creates themselves, whose input can't be known at seed time. The rows still serve their purpose -- demonstrating the cache format and giving the audit log real `ai.*` entries to show.

## Final status

**What works:** The full Who-method pipeline end to end -- scorecard authoring and approval,
candidate intake with email dedupe, every stage gate (sourced through hired, plus reject/withdraw
from any active stage), a chairman-only override with a mandatory reason that's permanently
audited, interviewer assignment and all four interview-type forms, a ratings matrix whose
visibility rule is enforced exactly as specified, named references and safeguarding checks,
decisions and sell plans, a printable decision record with a full audit trail, a chairman
dashboard with compliance reporting and a filterable audit log, four AI-assisted drafting features
(all live-tested against real Groq/Gemini traffic, not just mocks) that are fully inert with
`AI_ENABLED=false`, an idempotent seed script covering every scenario the spec names, a one-click
demo-reset flow, and a guided home-page tour -- all 52 pytest tests pass, and every phase was
smoke-tested against the real Neon database, not just imported successfully.

**Known limitations:**
- No real authentication -- the role switcher is explicitly a demo stand-in, not a security boundary.
- No concurrency handling: two people editing the same scorecard or interview at once will silently overwrite each other (last write wins); fine for a single school's small hiring team, not for a larger deployment.
- The decision record and audit log have no pagination; both would need it well before thousands of events accumulate.
- `OpeningStatus` (draft/open/filled/closed) is informational only -- no gate depends on it, so nothing stops sourcing candidates against a `draft` opening.
- Reorder-by-swap on the scorecard editor only swaps adjacent positions one step at a time; fine for the handful of items a real scorecard has, tedious for a much longer list.
- The AI evidence-mapping eval script's precision/recall numbers are only as good as 3 hand-labelled samples -- illustrative, not a rigorous benchmark.
- Render deployment was prepared (`render.yaml`, README steps) but not actually performed, per the prompt's "do not deploy."

**What I'd do with more time:**
- Real authentication (even a simple email-link or password flow) and per-user sessions instead of a cookie-selected demo identity.
- Optimistic locking (an `updated_at` check on write) on the handful of records multiple roles can edit, so a stale save fails loudly instead of silently overwriting.
- Pagination and date-range filtering on the audit log and decision record once event volume justifies it.
- A gate tying `OpeningStatus` to whether candidates can be sourced against it, and a small state machine for opening status transitions instead of a free-choice dropdown.
- Drag-and-drop (or at least multi-step) reordering for scorecard items.
- A larger, blind-labelled evaluation set for the evidence-mapping feature, run across both providers, to actually compare Groq vs. Gemini quality rather than just confirming both work.
- Email notifications (an interviewer assigned, a reference completed, a decision recorded) -- explicitly out of scope here but the natural next feature for a real deployment.
