## Phase 1: Schema fixes, rules engine, audit, tests

What I built:
- Migration `bfb17928e2c7` ("cascade and candidate email"): `Scorecard -> ScorecardItem` and `RoleOpening -> Scorecard` FKs are now `ON DELETE CASCADE` (both DB-level and the matching ORM `cascade="all, delete-orphan"`); `Application -> RoleOpening` and `Application -> Candidate` are explicit `ON DELETE RESTRICT`; `candidates.email` got a unique constraint. Recorded the RESTRICT rule in `CLAUDE.md`.
- `Candidate.email` gets an `@validates("email")` hook that lowercases and strips before it's written, so `"Jane@X.com "` and `"jane@x.com"` collide correctly against the new unique constraint.
- `app/services/gates.py`: a `GateResult(allowed, reasons)` dataclass and one pure function per forward transition (`sourced->screening` through `decision->offer`; `offer->hired` has no gate). `check_gate(application, target_stage)` dispatches by target stage. No DB access — everything reads relationships assumed to be already loaded.
- `app/services/audit.py`: single `log_event(...)` function. No update/delete functions exist in the module by design.
- `app/services/workflow.py`: `advance_application` (validates the move is the single next stage or reject/withdraw, runs the gate, applies the change, logs it; supports chairman-only override with a reason), `release_interviewer` (hiring manager or chairman only, reason required), `approve_scorecard` / `assert_scorecard_editable`, and `create_default_safeguarding_checks` (wired to fire automatically the moment an application enters the `references` stage).
- `app/services/visibility.py`: `can_view_ratings(user, interview)` — chairman/HR/hiring manager always see ratings; an interviewer only sees the application's ratings matrix once they've submitted at least one rating of their own on that application.
- `DEFAULT_SAFEGUARDING_CHECKS` added to `app/config.py` as a plain module constant (not an env-driven setting).
- 37 pytest tests across `tests/test_gates.py` and `tests/test_workflow.py`, built on in-memory model objects via `tests/factories.py` (no database). Added `pytest==8.3.4` via `requirements-dev.txt` (`-r requirements.txt` + pytest), per the "pytest as a dev dependency" allowance.

Problems I hit and how I fixed them:
- The autogenerated migration created foreign keys and the unique constraint with no explicit names (`op.create_foreign_key(None, ...)`), which made `downgrade()` uncallable (`drop_constraint(None, ...)`). Gave them explicit names matching Postgres's own default naming convention in both directions.
- First test run failed: in-memory `Application()` objects had `stage=None` instead of the model's declared default. SQLAlchemy's `mapped_column(default=...)` only applies at INSERT/flush time, not on plain Python construction — fixed by having the test factory set `stage=ApplicationStage.sourced` explicitly.
- Two gate tests failed the same way: `gate_focused_to_references` compared `rating.scorecard_item_id` (the raw FK scalar), which likewise is only populated by a flush, not by assigning the `scorecard_item` relationship in memory. Fixed by comparing `rating.scorecard_item.id` instead, which is populated immediately since it's a direct object reference. Also fixed the same latent bug in `workflow.create_default_safeguarding_checks`, which was setting `application_id=application.id` instead of `application=application` — the former wouldn't show up in `application.safeguarding_checks` until a DB round-trip, which would have silently broken the very next gate check in the same request.

Decisions I made:
- `advance_application`'s `override_reason` behavior: a non-chairman actor supplying any override reason raises `WorkflowError` ("refused" as an authorization error); a chairman supplying a blank/missing override reason against a blocked gate just falls through to the normal blocked `GateResult` (no exception) — the prompt's "refused" for that case reads as "the move does not happen," not "a wrong-role security violation," so only the wrong-role path raises.
- Invalid stage transitions (skipping a stage, moving backward, or acting on an application already in a terminal stage) raise `WorkflowError`, not a `GateResult` — these are programming/UI errors (the UI should only ever offer the valid next move), not a business-rule judgment call with reasons to show a user.
- `reject`/`withdraw` go through `advance_application` as well, as a separate branch (reason required, no gate function, allowed from any non-terminal stage) rather than a separate service function — keeps the single "the one way state changes happen" entry point from the prompt's "every state change goes through app/services."
- `can_view_ratings` treats "submitted their own rating" as: the user has at least one rating recorded on any interview of theirs for that application (not necessarily the specific `interview` argument) — matches "after submitting their own" without requiring them to have rated every scorecard item first.

## Phase 3: Core workflow screens

What I built:
- Shared partials: `partials/stage_tracker.html` (7-step tracker mapped from `ApplicationStage`, with a collapsible "Why this step?" note per stage) and `partials/gate_panel.html` (renders `GateResult.reasons`). `base.html` also gained a flash-message block and nav links (Openings always; My interviews for interviewers; Dashboard/Audit log for chairman, routes land in Phase 4).
- `app/dependencies.py` gained `get_flash`/`set_flash`: a short-lived `rubric_flash` cookie carries one message across a redirect, read once and cleared by `get_template_context`.
- `app/routers/_common.py`: shared `load_application`/`load_interview` loaders with the full eager-load graph (scorecard+items, interviews+interviewer+ratings+scorecard_item, references, safeguarding_checks+verified_by, decision+decided_by, sell_plan), used by every router below so gates and templates never trigger N+1 lazy loads or operate on partially-loaded objects.
- `app/routers/openings.py`: list (status/type filters), create (principal defaults to self as hiring manager; chairman picks one), detail (scorecard mission/items editor with add/edit/delete/reorder, approve, read-only once approved, candidate pipeline grouped by stage), and an opening-status control (draft/open/filled/closed) so the list filter has something to filter on.
- `app/routers/candidates.py`: add-candidate form that looks up by normalized email and reuses the existing `Candidate` row instead of creating a duplicate; blocks a second application to the same opening.
- `app/routers/applications.py`: the application hub page (tracker, gate panel, advance/reject/withdraw, chairman-only override, interview list + assign form, ratings matrix, references list + add form, safeguarding checklist, decision form, sell plan form), plus the printable decision record with a collected audit trail spanning the application and all of its interviews/references/checks/decision/sell-plan rows.
- `app/routers/interviews.py`: assign-by-type, the three interview-type forms (screening pass/fail, Who with the book's 5 chronological questions plus inline reference-naming, focused/demo-lesson with a grade+evidence field per scorecard item), release-interviewer, and `/my-interviews`.
- `app/routers/references.py` / `app/routers/safeguarding.py`: name/conduct/complete a reference with the book's 5 questions as a guide; clear/flag a safeguarding check with notes and who verified it.
- `app/services/permissions.py` gained `can_name_reference` (see below).

Problems I hit and how I fixed them:
- **Cascade-on-construct silently failed to add new children to the session.** Writing `parent.child = Child(parent=parent, ...)` (passing the parent via constructor kwarg, then immediately re-assigning the result to the parent's attribute) does not reliably fire SQLAlchemy's save-update cascade — confirmed by reproducing it directly against the real Neon DB (`sc in db` was `False` right after construction, with an `SAWarning: ... add operation ... will not proceed`). Everywhere else in the routers I'd already called `db.add(child)` explicitly, which sidesteps the issue entirely; the three spots that didn't (`Scorecard` on mission save, `Decision`, `SellPlan`) got an explicit `db.add()` added. This surfaced as a 500 (`NotNullViolation` on `audit_events.entity_id`, because the un-added child's `.id` stayed `None` after `flush()`) during the first end-to-end smoke test, not from unit tests (which don't touch a real session) — a reminder that gate/workflow unit tests passing is not the same as the routes being correct.
- **The Who interview form couldn't name references.** Phase 2 defined `can_manage_references` as chairman/HR only, but Phase 3 item 5 explicitly wants the Who interviewer to add the references the candidate names, live, from that form. Added a narrower `permissions.can_name_reference(user, application)`: true for chairman/HR (who can do anything reference-related) or the specific user currently assigned as that application's Who interviewer. The broader reference-interview-and-complete flow stays chairman/HR-only.
- Ran a full manual walkthrough over real HTTP against the live Neon database (not just pytest) because Phase 3 is almost entirely routes/templates with no new pure-function logic to unit-test: created an opening as principal, built and approved a scorecard, added a candidate, and drove one application all the way to `hired` (screening pass -> Who interview + 2 named references -> focused interview with graded evidence -> references completed + all 4 safeguarding checks cleared -> decision -> sell plan -> hired), then separately verified: the one-reference gate block, the two-references-no-former-manager block (covered by existing pytest, re-confirmed live), a chairman override succeeding while the same override attempt by a principal is refused with no audit row written at all, the ratings-matrix visibility rule (a second interviewer's view of another's ratings is literally the string "Hidden until you submit your own ratings" until they submit their own, then it shows the other interviewer's evidence), cross-opening/cross-interviewer 403s, and interviewer release. Decision record page and `/my-interviews` also checked. No 500s remained in the server log by the end.

Decisions I made:
- The opening-status control (draft/open/filled/closed) wasn't explicitly requested by this phase, but the openings list asks to filter by status and every opening would otherwise sit in `draft` forever with nothing to filter — added a minimal select-and-save control gated by the same permission as scorecard management, logged to the audit trail like everything else.
- The application detail page is one large template rather than several smaller ones for interviews/references/safeguarding/decision/sell-plan, since they're all sub-sections of the same hub a Chairman or principal scans top-to-bottom; kept each section visually separate with its own heading and permission-gated controls instead.
- Sell plan is only offered once `Decision.outcome == hire`, since selling an offer to someone you're not hiring doesn't make sense; there's no DB gate for this (sell plan has no stage dependency in the spec), so it's purely a template-level condition.
- The test users/openings/applications created while smoke-testing against the live Neon database were left in place rather than manually truncated — Phase 6's seed script will `TRUNCATE ... RESTART IDENTITY CASCADE` and replace them with the real seed data; deleting them now would be an unrequested destructive action against the only database available, outside of what this phase calls for.
- Added one pytest test for the new `can_name_reference` predicate (44 total); the 12 screens themselves are routes/templates verified by the live walkthrough above, not meaningfully unit-testable in isolation without a database.

## Phase 4: Chairman dashboard

What I built:
- `app/routers/dashboard.py`: `GET /dashboard` (chairman-only, 403 otherwise) with openings-by-stage counts, hires to date, average days from opening creation to the `application.advance` audit event that recorded `to_stage: hired` (not from candidate-sourced date, since the spec says "opening to hire"), an overrides table (who/when/gate bypassed/the gate's own reasons/the stated override reason), released interviewers with their reasons, and applications with no activity in 14+ days.
- `GET /audit-log`: filterable by opening, user, action, and an "overrides only" checkbox; the opening filter resolves to the opening's own id plus every Interview/Reference/SafeguardingCheck id under its applications, since `AuditEvent` is polymorphic (`entity_type` + `entity_id`) with no FK.
- "Last activity" for the stale-applications check is `max()` over each child row's own `updated_at` (interviews, references, safeguarding checks, decision, sell plan) plus the application's own — simpler and just as accurate as re-deriving it from the audit log, since every mutation already touches a row's `updated_at` via the `TimestampMixin`.

Problems I hit and how I fixed them:
- First version of the opening filter on `/audit-log` crashed with `AttributeError: 'int' object has no attribute 'id'` — `db.scalars(select(Application.id).where(...))` already yields plain ints (selecting a single column, not the ORM object), so `{a.id for a in ...}` was wrong; fixed to `set(db.scalars(...))`. Caught by the live walkthrough, not a unit test, since this phase is routes/queries over real data like Phase 3.
- Also found and killed two stray `uvicorn` processes left over from the very first setup session (still listening on port 8000) and a runaway interactive Anaconda Python REPL spawned by my own empty-heredoc typo in a shell command — none were related to the app itself, just session hygiene.

Decisions I made:
- No new pytest tests: everything new here is either a template-rendered aggregation query (verified live, same reasoning as Phase 3) or reuses existing permission predicates (`can_view_dashboard`/`can_view_audit_log`, already covered in `test_permissions.py`).
- Average days to hire is computed from `RoleOpening.created_at`, exactly as the spec's phrase reads ("average days from opening to hire"), even though in a real school the opening might sit in `draft` for a while before going `open` — out of scope to track an explicit "opened_at" timestamp when the spec didn't ask for one.
