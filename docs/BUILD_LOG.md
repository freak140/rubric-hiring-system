## Phase 1: Schema fixes, rules engine, audit, tests

What I built:
- Migration `bfb17928e2c7` ("cascade and candidate email"): `Scorecard -> ScorecardItem` and `RoleOpening -> Scorecard` FKs are now `ON DELETE CASCADE` (both DB-level and the matching ORM `cascade="all, delete-orphan"`); `Application -> RoleOpening` and `Application -> Candidate` are explicit `ON DELETE RESTRICT`; `candidates.email` got a unique constraint. Recorded the RESTRICT rule in `CLAUDE.md`.
- `Candidate.email` gets an `@validates("email")` hook that lowercases and strips before it's written, so `"Jane@X.com "` and `"jane@x.com"` collide correctly against the new unique constraint.
- `app/services/gates.py`: a `GateResult(allowed, reasons)` dataclass and one pure function per forward transition (`sourced->screening` through `decision->offer`; `offer->hired` has no gate). `check_gate(application, target_stage)` dispatches by target stage. No DB access — everything reads relationships assumed to be already loaded.
- `app/services/audit.py`: single `log_event(...)` function. No update/delete functions exist in the module by design.
- `app/services/workflow.py`: `advance_application` (validates the move is the single next stage or reject/withdraw, runs the gate, applies the change, logs it; supports chairman-only override with a reason), `release_interviewer` (hiring manager or chairman only, reason required), `approve_scorecard` / `assert_scorecard_editable`, and `create_default_safeguarding_checks` (wired to fire automatically the moment an application enters the `references` stage).
- `app/services/visibility.py`: `can_view_ratings(user, interview)` — chairman/HR/hiring manager always see ratings; an interviewer only sees the application's ratings matrix once they've submitted at least one rating of their own on that application.
- `DEFAULT_SAFEGUARDING_CHECKS` added to `app/config.py` as a plain module constant (not an env-driven setting).
- 37 pytest tests across `tests/test_gates.py` and `tests/test_workflow.py`, built on in-memory model objects via `tests/factories.py` (no database). Added `pytest==8.3.4` via `requirements-dev.txt` (`-r requirements.txt` + pytest), per the "pytest as a dev dependency" allowance.

Problems I hit and how I fixed them:
- The autogenerated migration created foreign keys and the unique constraint with no explicit names (`op.create_foreign_key(None, ...)`), which made `downgrade()` uncallable (`drop_constraint(None, ...)`). Gave them explicit names matching Postgres's own default naming convention in both directions.
- First test run failed: in-memory `Application()` objects had `stage=None` instead of the model's declared default. SQLAlchemy's `mapped_column(default=...)` only applies at INSERT/flush time, not on plain Python construction — fixed by having the test factory set `stage=ApplicationStage.sourced` explicitly.
- Two gate tests failed the same way: `gate_focused_to_references` compared `rating.scorecard_item_id` (the raw FK scalar), which likewise is only populated by a flush, not by assigning the `scorecard_item` relationship in memory. Fixed by comparing `rating.scorecard_item.id` instead, which is populated immediately since it's a direct object reference. Also fixed the same latent bug in `workflow.create_default_safeguarding_checks`, which was setting `application_id=application.id` instead of `application=application` — the former wouldn't show up in `application.safeguarding_checks` until a DB round-trip, which would have silently broken the very next gate check in the same request.

Decisions I made:
- `advance_application`'s `override_reason` behavior: a non-chairman actor supplying any override reason raises `WorkflowError` ("refused" as an authorization error); a chairman supplying a blank/missing override reason against a blocked gate just falls through to the normal blocked `GateResult` (no exception) — the prompt's "refused" for that case reads as "the move does not happen," not "a wrong-role security violation," so only the wrong-role path raises.
- Invalid stage transitions (skipping a stage, moving backward, or acting on an application already in a terminal stage) raise `WorkflowError`, not a `GateResult` — these are programming/UI errors (the UI should only ever offer the valid next move), not a business-rule judgment call with reasons to show a user.
- `reject`/`withdraw` go through `advance_application` as well, as a separate branch (reason required, no gate function, allowed from any non-terminal stage) rather than a separate service function — keeps the single "the one way state changes happen" entry point from the prompt's "every state change goes through app/services."
- `can_view_ratings` treats "submitted their own rating" as: the user has at least one rating recorded on any interview of theirs for that application (not necessarily the specific `interview` argument) — matches "after submitting their own" without requiring them to have rated every scorecard item first.

## Phase 2: Demo identity and permissions

What I built:
- `app/dependencies.py`: `get_current_user` reads the `rubric_user_id` cookie, loads that user, and falls back to the first chairman (by id) when the cookie is missing or points at a nonexistent id; raises a clear 500 if no users exist at all (tells you to run `scripts/seed.py`, which doesn't exist until Phase 6). `get_template_context` bundles `request`, `current_user`, and `all_users` for every page that needs the top-bar switcher.
- `app/routers/demo.py`: `POST /demo/switch-user` sets the cookie and redirects back to the referring page (falls back to `/`).
- `base.html`: the role-switcher `<select>` is now populated from real seeded users (name + role), auto-submits on change via a plain HTML form (works with JS off too, via a `<noscript>` fallback button — no HTMX needed for this), and a "Demo mode: no real logins" badge sits next to it.
- `app/services/permissions.py`: one pure predicate per capability from the spec (`can_create_opening`, `can_manage_scorecard`/`can_approve_scorecard`, `can_add_candidate`, `can_assign_interviewer`, `can_record_decision`/`can_record_sell_plan`, `can_manage_references`/`can_manage_safeguarding`, `can_view_dashboard`/`can_view_audit_log`, `can_override_gate`, `can_submit_rating`, `can_view_interview`). All take already-loaded objects, no DB access, mirroring `gates.py`'s style.
- 6 new pytest tests for permissions (43 total now).

Problems I hit and how I fixed them:
- The role-switcher dropdown rendered "Hr" instead of "HR" via `|title`. Special-cased it in the template rather than reach for a filter library (none is in requirements.txt).
- Phase 2 has nothing to seed real users yet (seeding is Phase 6), so there was no way to smoke-test the switcher against a running server. Inserted 4 throwaway users (one per role) directly via a one-off script, confirmed default-to-chairman, switching, and invalid-cookie fallback all work against the real Neon database, then left them in place — Phase 6's `TRUNCATE ... RESTART IDENTITY CASCADE` will replace them with the real seed data, so there's no cleanup to do now.

Decisions I made:
- `permissions.py` only has predicates for actions Phase 3+ will actually need to gate; I didn't pre-build a generic "can view this opening" catch-all since "hr: view everything" / "chairman: everything" just means those roles pass every predicate that matters, not that a separate blanket-view function is needed.
- Enforcement in routes/templates is deferred to Phase 3 as each screen is built (there are no protected actions yet to wire up) — the plan item is still checked off because the mechanism (cookie, dependency, permissions module) is complete and tested; the application is the thing that doesn't exist yet.
